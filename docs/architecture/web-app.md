## Web Application

The Web Application is the primary user-facing component of Best of JS, providing a browsable interface for exploring JavaScript project trends. This document details the architecture, features, and integration points of the web application within the broader Best of JS system.

## 1. Purpose and Role

The Best of JS Web Application serves as the public interface for displaying curated JavaScript projects and their trending data. It enables users to:

- Browse and search projects across various categories and tags
- View project details including star history and growth trends
- Compare projects within categories
- Create personal bookmarks for favorite projects (with GitHub sign-in)
- Discover rising projects in the JavaScript ecosystem

The application consumes data from the static API generated by the backend system and presents it through an intuitive web interface.

## 4. Key Features

### 4.1 Project Browsing and Discovery

The Web Application provides various ways to discover projects:

| Feature | Description |
| --- | --- |
| Tag Categorization | Browse projects by tags (e.g., framework, component, chart) |
| Trending Views | Filter projects by daily, weekly, monthly, or yearly growth |
| Hot Projects | Highlight projects with significant recent star growth |
| Search | Full-text search across projects |

Projects are organized by tags that classify them into relevant categories, making it easy to find related technologies.

#### Tags excluded from rankings

The home page and the `/trends/*` pages drop projects carrying any tag in `TAGS_EXCLUDED_FROM_RANKINGS` (`meta`, `learning`, `wildcard`, `ai-methodology`), via `findProjectsWithTrends()`'s `excludeTagCodes` option. The exclusion is editorial, not a quality signal: those projects are not libraries, so they would otherwise crowd out the ones a "Hot Projects" list exists to surface.

The `/projects` listing does **not** apply it, so a "View full rankings »" link can land on a different top 5 than the card it came from — most visibly on the yearly window. That divergence is known and deliberate: silently removing projects at the scale of Immich or freeCodeCamp from the main listing, with no visible affordance saying so, would be worse than the mismatch.

## 5. Integration with Other Systems

### 5.1 Data Sources

The Web Application reads project data two ways, and is mid-migration from the first to the second:

| Source | Surfaces |
| --- | --- |
| PostgreSQL, via `@repo/db` queries wrapped in `"use cache"` | Home page (hot lists, recently added, popular tags, catalog stats), `/trends/*`, `/projects` and its detail pages (NPM dependency lists included), `/featured`, `/tags`, `sitemap.ts`, `/api/stats`, `/api/tags/[slug]`, the OG image routes except the monthly-rankings one |
| Static JSON generated by the backend (`@/server/api`, `@/server/api-remote-json`) | `/rankings/monthly` and its OG image, the monthly-rankings home card, the search palette's `/api/search-data` index |

DB-backed surfaces still never query on request in the general case: every query sits behind a cached function tagged for invalidation by the backend tasks (`daily`/`home` for the home and trends pages, `projects` for the listing), so a page render is a cache read unless the tag was just invalidated.

### 5.1.1 Cache invalidation and the daily job

The daily job is a strict chain, so every refresh of the app follows the data it depends on. See `docs/architecture/backend-app.md` for the full pipeline; the part that matters here:

1. `daily-update-trends` recomputes `repo_trends` / `project_trends`, then invalidates `daily` and `home` (`invalidate-trends-cache`) — the DB-backed home and `/trends` pages pick up the new ranking immediately.
2. It then triggers the static API build on Vercel, whose build command rebuilds the web app (`build-project-data` bakes `projects.json` in at build time) and invalidates the remaining tags.

Step 1 is redundant with step 2 in the happy path, and deliberately so: it keeps the DB-backed surfaces from waiting on — or being stranded by — a static API build they don't otherwise depend on.

The web app is still rebuilt daily only because of `build-project-data`. Once the surfaces in the table above migrate off the static JSON, the rebuild can go and step 2 becomes a leaf that serves external consumers only.
